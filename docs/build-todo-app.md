# Todo アプリの構築手順

Azure VM（Ubuntu 24.04 LTS）に Todo アプリを構築します。**受講者自身の Azure サブスクリプションで実行する手順です。**

**本書は手順書です。** ポート番号やタイムアウトの値、設計の理由は[設計書](design.md)を参照してください。

**同じ環境を Terraform で自動構築する[コース内ラボ](../labs/sections/section09/README.md)があります。** ただし**コース内ラボ環境（Udemy のワークスペース）での実施が前提**で、ご自身のサブスクリプションで実行すると利用料金が発生します。ここでの手作業の手順と、ラボが自動化する範囲の対応は、ラボ側にまとめています。

## 前提条件

**作業はすべて Azure Cloud Shell（Bash）で行います。** 開発 PC に何かを導入する必要はありません。

| 項目                     | 内容                                     |
| ------------------------ | ---------------------------------------- |
| ブラウザ                 | Azure ポータルにサインインできること     |
| Azure サブスクリプション | リソースを作成できる権限があること       |
| Cloud Shell              | Bash。ストレージなし（エフェメラル）で可 |

**Cloud Shell は 20 分の無操作でタイムアウトします。** エフェメラルセッションでは、そのときアップロードしたファイルも消えます。作業は続けて進めてください。

## 構成

| 項目             | 値                                             |
| ---------------- | ---------------------------------------------- |
| OS イメージ      | Ubuntu Server 24.04 LTS                        |
| VM サイズ        | `Standard_F1as_v7`                             |
| 管理者ユーザー名 | `azureuser`                                    |
| 認証の種類       | SSH 公開キー                                   |
| NSG（受信規則）  | 22/tcp は Cloud Shell の IP、80/tcp は制限なし |

**80 番はインターネットへ公開します。** SSH（22 番）だけは許可した IP に絞ります。

**このアプリにはログイン認証がありません。** URL に到達した人は誰でもタスクを追加・削除できます。**動作確認用のタスク以外を入力せず、確認が終わったらリソースグループごと削除してください。**

## 手順

上から順に実行してください。

### 1. Cloud Shell を開く

Azure ポータル右上の **Cloud Shell** アイコン（`>_`）を選び、**Bash** を選択します。ストレージの確認を求められたら「**ストレージ アカウントは必要ありません**」を選びます。

<https://shell.azure.com> から直接開くこともできます。

**以降のコマンドは、断りがない限り Cloud Shell で実行します。**

### 2. Azure SQL Database の作成

Azure ポータルで作成します。**無料オファーの設定を 1 か所だけ間違えると課金されます。** 下の項目 4 を必ず確認してください。

1. 「SQL データベース」から新規作成を開始します
2. リソースグループとデータベース名（例: `todo`）を指定します
3. サーバーを新規作成します。認証方法は **SQL 認証** を選び、サーバー管理者ログインのユーザー名とパスワードを控えます
4. コンピューティングとストレージで **サーバーレス** を選び、**無料オファーを適用します**。「制限に達したとき」の動作は **「データベースを自動一時停止する」** を選びます

   > 「課金して継続」を選ぶと、無料枠を超えた分が課金されます。しかも**同一の請求期間内は無料枠に戻せません。**

5. 自動一時停止の遅延は既定の **60 分** のままにします
6. ネットワークの設定でパブリックエンドポイントを有効にし、「**現在のクライアント IP アドレスを追加する**」を「はい」にします
7. 作成を完了します

このサーバー管理者ログインを、アプリの接続にもそのまま使います。アプリ専用のユーザーは作りません。

**この手順でテーブルは作りません。** アプリが最初のアクセスのときに `dbo.todos` を作成します。

### 3. Azure VM の作成

Azure ポータルで仮想マシンを作成します。

1. イメージに **Ubuntu Server 24.04 LTS** を選びます
2. サイズは `Standard_F1as_v7` を選びます
3. 管理者アカウントの認証の種類は **SSH 公開キー**、ユーザー名は `azureuser` にします
4. キーペアを新規作成し、秘密鍵ファイル（`ssh-key.pem`）をダウンロードします。**再ダウンロードはできません**
5. 受信ポートは **HTTP (80)** と **SSH (22)** を許可します
6. 作成を完了し、パブリック IP アドレスを控えます

### 4. 受信規則の絞り込み

**VM を作った直後は、22 番と 80 番が全世界へ開いています。** このうち **22 番だけ**を絞ります。

Azure ポータルで VM の「ネットワーク設定」を開き、受信規則を編集します。

| ポート | 用途                   | ソースの選び方                                               |
| ------ | ---------------------- | ------------------------------------------------------------ |
| 22     | Cloud Shell からの SSH | **IP Addresses** を選び、下で調べた Cloud Shell の IP を入力 |
| 80     | ブラウザからのアクセス | **変更しません**（`Any` のまま）                             |

**80 番はそのままにします。** 理由は[設計書の「経路ごとの仕様」](design.md#経路ごとの仕様)を参照してください。

**22 番の IP は手で入力します。** 接続元が Cloud Shell（Azure 側のコンテナ）で、ブラウザとは別のアドレスだからです。Cloud Shell で実行して控えてください。

```bash
curl -s https://api.ipify.org
```

**ブラウザで調べた IP を入れないでください。** Cloud Shell の送信元とは別のアドレスです。取り違えると SSH で接続できません。

### 5. 秘密鍵と接続情報の配置

**VM へ持ち込むファイルを、ここでまとめて用意します。** 秘密鍵と接続情報の 2 つです。**すべて Cloud Shell で行います。**

#### 5-1. 秘密鍵を配置する

手順 3 でダウンロードした `ssh-key.pem` を Cloud Shell へアップロードします。

1. Cloud Shell のツールバーから **「ファイルのアップロード/ダウンロード」→「アップロード」** を選びます
2. `ssh-key.pem` を選択します

アップロードした鍵を `~/.ssh/` へ移し、**所有者だけが読める権限にします。**

```bash
mkdir -p ~/.ssh
mv ssh-key.pem ~/.ssh/
chmod 400 ~/.ssh/ssh-key.pem
```

**`chmod 400` を飛ばすと SSH が鍵を受け付けません。** アップロード直後のファイルは他のユーザーからも読める権限になっており、SSH は「保護されていない鍵」とみなして接続を拒否します。

#### 5-2. `.env` を作る

**[コース内ラボ](../labs/sections/section07/README.md)から進んできた場合、この手順は不要です。** `terraform apply` が接続情報を `~/mssql-todo-app/src/.env` へ書き出しています。5-3 へ進んでください。

```bash
code ~/.env
```

Cloud Shell のエディタが開きます。手順 2 で控えた値を貼り付け、`Ctrl` + `S` で保存して `Ctrl` + `Q` で閉じます。

```text
DB_HOST=<サーバー名>.database.windows.net
DB_NAME=todo
DB_USER=<管理者ユーザー>
DB_PASSWORD=<パスワード>
```

パスワードに `@` や `:` が含まれていても、そのまま記入して問題ありません。アプリ側で正しくエスケープします。

**`code` は Cloud Shell に組み込まれたエディタです。** ブラウザ上で動くため、貼り付けは手元の OS の操作（`Cmd` + `V` または `Ctrl` + `V`）がそのまま使えます。

#### 5-3. VM へ送る

```bash
scp -i ~/.ssh/ssh-key.pem ~/.env azureuser@<VM のパブリック IP>:~/
```

初回は接続先の確認を求められるので `yes` と入力します。

**送り先は VM のホームディレクトリです。** アプリの置き場所（`/opt/todo`）はまだ存在せず、作られたあとも `azureuser` には書き込む権限がありません。**取り込みは手順 9 のスクリプトが行います。**

### 6. SSH 接続

```bash
ssh -i ~/.ssh/ssh-key.pem azureuser@<VM のパブリック IP>
```

**接続先の確認は求められません。** 手順 5-3 の `scp` で応答済みのためです。

**接続できない場合は**[トラブルシュートの「SSH で接続できない」](troubleshooting.md#ssh-で接続できない)を参照してください。

### 7. VM の送信元 IP を SQL へ登録

**SSH で VM に接続した状態で**実行します。VM が Azure SQL Database へ接続するときの送信元 IP アドレスを調べます。

```bash
curl -s https://api.ipify.org
```

表示された IP アドレスを、Azure ポータルで SQL サーバーの「ネットワーク」を開き、ファイアウォール規則へ追加して保存します。

**この手順を飛ばすと、接続情報が正しくてもデータベースに到達できません。** アプリの画面には「データベースに接続できません」とだけ表示され、原因が分かりません。

**Cloud Shell の IP でもブラウザの IP でもありません。** VM 自身の送信元アドレスです。

### 8. アプリの取得

**SSH で VM に接続した状態で**実行します。ホームディレクトリに `mssql-todo-app/` ができます。

```bash
sudo apt-get update && sudo apt-get install -y git
git clone --depth 1 --sparse https://github.com/m-oka-system/mssql-todo-app.git
cd mssql-todo-app
git sparse-checkout set src deploy
```

**Ubuntu Server のイメージに git は含まれません。** 1 行目で導入します。

**`Could not get lock` で失敗した場合は、1 分ほど待って同じコマンドを実行してください。** 作成直後の VM では自動更新が動いていることがあります。

**VM に置くのは、アプリの実行に必要なファイルだけです。** 範囲と理由は[設計書の「VM へ取得する範囲」](design.md#vm-へ取得する範囲)を参照してください。

**`src/.env` はリポジトリに含まれません。** `.gitignore` の対象のため、手順 5-3 で送ったファイルを次の手順で取り込みます。

### 9. セットアップスクリプトの実行

手順 8 に続けて、VM 上で実行します。**手順 5-3 で送った `.env` のパスを渡します。**

```bash
sudo deploy/setup.sh --env-file ~/.env
```

スクリプトは次の作業をまとめて行います。完了まで数分かかります。

1. ODBC Driver 18 の導入
2. nginx の導入
3. エディタ（`micro`）の導入
4. uv の導入（`/usr/local/bin/uv`）
5. 実行ユーザー `todo` の作成とアプリの `/opt/todo` への配置
6. **接続情報の `/opt/todo/src/.env` への配置**
7. 依存パッケージのインストール
8. systemd サービスの登録と起動
9. nginx の設定と起動

**`--env-file` を渡すと、配置先・所有者・パーミッションを自分で指定せずに済みます。** スクリプトが `todo` の所有・600 で置きます。**サービスを起動する時点で `.env` が揃うため、あとから再起動する必要もありません。**

**`--env-file` を省いても正常に完了します。** その場合 `/opt/todo/src/.env` は空欄のままになり、あとから記入して再起動することになります。起動確認には `/healthz` を使っており、この URL はデータベースに接続しません。

最後に「セットアップが完了しました」と表示されれば成功です。

送ったファイルには接続情報が残るため、消しておきます。

```bash
rm ~/.env
```

**あとから値を直したいときは、VM 上で直接編集できます。** 手順は[トラブルシュートの「データベースに接続できませんと表示される」](troubleshooting.md#データベースに接続できませんと表示される)にあります。

### 10. ブラウザからの確認

```text
http://<VM のパブリック IP>
```

タスクの追加、完了状態の変更、削除がすべて動作すれば完了です。

**画面の下端には実行環境の情報が出ます。** 応答した VM のホスト名とプライベート IP、接続先のデータベース名を表示します。仕様は[設計書の「実行環境の表示」](design.md#実行環境の表示)を参照してください。

**同じ情報は `curl http://<VM のパブリック IP>/healthz` でも取得できます。** どの VM が応答したかだけを繰り返し確かめたい場合は、こちらのほうが手早く読めます。

**表示されたデータベース名を、Azure ポータルで作成したデータベースと見比べてください。** 画面には `.env` に記入した値がそのまま出るため、`.env` と見比べても記入の誤りは分かりません。取り違えたまま接続できた場合、そちらにテーブルが作られて画面は正常に見えます。

**初回の表示に 1 分ほどかかる場合があります。** 異常ではありません。理由は[トラブルシュートの「初回アクセスが遅い」](troubleshooting.md#初回アクセスが遅い)を参照してください。

**開くアドレスは、手順 6 の SSH で使ったものと同じ**（VM のパブリック IP）です。

**画面が表示されない場合は**[トラブルシュートの「ブラウザから VM にアクセスできない」](troubleshooting.md#ブラウザから-vm-にアクセスできない)を確認してください。

## VM 再起動後の動作

systemd に登録済みのため、VM を再起動してもアプリは自動的に復帰します。手動での起動操作は不要です。

## アプリを更新したとき

リポジトリが更新されたときの手順は[`deploy/README.md`](../deploy/README.md)にあります。VM 上で 1 行実行するだけです。

## 後片付け

**確認が終わったら、Azure ポータルでリソースグループごと削除してください。** 環境を残すとデータベースの無料枠を消費し続けます。影響は[要件定義の「環境を放置した場合の影響」](requirements.md#環境を放置した場合の影響)を参照してください。

**Cloud Shell に残る秘密鍵と接続情報も消してください。**

```bash
rm -f ~/.ssh/ssh-key.pem ~/.env
```

**VM を削除しても、この 2 つは残ります。** ストレージなし（エフェメラル）で使っている場合はセッションとともに消えますが、マウントしている場合はファイル共有に残り続けます。

## 手元で動かす場合

**作成者向けの手順です。** 受講者は VM 上で動かします。

```bash
uv sync
cp src/.env.sample src/.env   # 接続情報を記入する
uv run python src/app.py      # http://127.0.0.1:5000
```

接続先の Azure SQL Database は、ファイアウォール規則で実行元の IP を許可しておく必要があります。
