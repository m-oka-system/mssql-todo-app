# トラブルシュート

- 対象: Todo アプリ（Flask + Azure SQL Database）
- 前提: [構築手順](build-todo-app.md)

**手順どおりに進めて動かないときの対処をまとめます。** 症状から探してください。

## まず実行するコマンド

**アプリの画面にはエラーの詳細を表示しません。** ODBC のエラーメッセージにはサーバー名やユーザー名が含まれるためです。原因はサーバーのログでしか分かりません。

VM に SSH で接続して実行します。

| 目的                 | コマンド                             | 期待する結果                     |
| -------------------- | ------------------------------------ | -------------------------------- |
| ログの確認           | `sudo journalctl -u todo -f`         | 例外のトレースバックが確認できる |
| サービスの状態確認   | `systemctl status todo`              | `Active: active (running)`       |
| アプリの死活確認     | `curl http://127.0.0.1:8000/healthz` | ホスト名を含む JSON              |
| 待ち受けアドレス確認 | `sudo ss -ltnp \| grep 8000`         | `127.0.0.1:8000` になっている    |
| nginx の状態確認     | `systemctl status nginx`             | `Active: active (running)`       |

`journalctl -f` は新しいログを表示し続けます。**ログを見ながらブラウザを操作すると、どの操作で何が起きたかが分かります。** アクセスログも同じ場所に出ます。終了は `Ctrl + C` です。

**`/healthz` はデータベースに接続しません。** ここが応答するのに画面がエラーになる場合、原因はアプリではなくデータベースへの接続です。切り分けに使ってください。

待ち受けが `0.0.0.0:8000` になっている場合、`todo.service` の `--bind` が効いていません。認証のないアプリが nginx を経由せずに公開されている状態です。

## 初回アクセスが遅い

**原因** — Azure SQL Database のサーバーレス構成は、無操作が続くと自動的に一時停止します。**停止中のデータベースへ接続すると、再開が終わるまで待たされます。** 仕組みは[設計書の「接続の再試行」](design.md#接続の再試行)を参照してください。

**影響** — アプリが接続をやり直すため、表示まで**待たされます。実機では 50 秒前後で表示されました。** その間、ブラウザは読み込み中のままになります。

**対処** — 待ってください。異常ではありません。2 分以上待っても復帰しない場合は、次項を確認してください。

自動一時停止は意図した設計です。**アプリと nginx のタイムアウトは、この待ち時間に合わせて設定しています。** 値と理由は[設計書の「タイムアウト」](design.md#タイムアウト)を参照してください。

## 「データベースに接続できません」と表示される

画面に次のメッセージが出た場合です。

```text
データベースに接続できません。src/.env の接続情報と、Azure SQL Database の
ファイアウォール規則にクライアント IP が登録されているかを確認してください。
```

原因は 5 つ考えられます。上から順に確認してください。

| 順  | 原因                             | 確認方法                                         | 対処                                            |
| --- | -------------------------------- | ------------------------------------------------ | ----------------------------------------------- |
| 1   | ファイアウォール規則に IP がない | VM 上で `curl -s https://api.ipify.org`          | 表示された IP を SQL サーバーの規則へ追加します |
| 2   | `.env` の記入誤り                | `sudo journalctl -u todo -n 50 --no-pager`       | サーバー名・ユーザー名・パスワードを修正します  |
| 3   | データベースが停止中             | 1 分ほど待って再読み込みする                     | 前項を参照します                                |
| 4   | 無料 vCore 秒の枯渇              | Azure ポータルでデータベースの使用量を確認します | **翌月まで復旧しません**                        |
| 5   | テーブルの定義が古い             | 上の 4 つに当てはまらない場合                    | 次項を参照します                                |

**原因 1 で確認するのは VM の送信元 IP です。** Cloud Shell の IP でもブラウザの IP でもありません。**VM に SSH で接続した状態で**実行してください。

**原因 3 と原因 4 は、画面上は区別できません。** 無操作による停止は接続を試みれば再開しますが、枯渇による停止は**その月の残りは再開しません。** 何度やり直しても復旧しない場合は、使用量を確認してください。

**原因はログのエラー番号で切り分けます。** 画面のメッセージは 5 つとも同じです。

| ログに出るエラー      | 意味                             | 待つと直るか     |
| --------------------- | -------------------------------- | ---------------- |
| `40615`               | ファイアウォール規則に IP がない | 直りません       |
| `18456`               | ユーザー名かパスワードの誤り     | 直りません       |
| `40613`               | データベースが利用できない       | 直ります         |
| `HYT00`               | ログインのタイムアウト           | **場合による**   |
| `Invalid column name` | テーブルの定義が古い             | 直りません       |
| `Invalid object name` | 削除したあと再起動していない     | 再起動で直ります |

**`HYT00` は 2 つの原因で出ます。** データベースが再開中の場合と、**サーバー名の誤りやネットワークの不達**の場合です。アプリからは区別できないため、どちらも再試行して待ちます。

`HYT00` が出て待っても直らないときは、**まず `DB_HOST` の綴りを確認してください。** 存在しないサーバー名でも、エラーは即座には返らず 15 秒待ってから `HYT00` になります。

接続情報を直したあとは、サービスを再起動してください。**接続情報はアプリの起動時に読み込みます。**

```bash
sudo -u todo micro /opt/todo/src/.env
sudo systemctl restart todo
```

## テーブルを作り直したい

**原因** — アプリのテーブル定義が改訂されたのに、データベースには古い定義のテーブルが残っています。**アプリは、テーブルが既にあると作り直しません。**

**影響** — 画面には「データベースに接続できません」と表示されます。接続そのものは成功しているため、接続情報を確認しても直りません。

**対処** — テーブルを削除してから、アプリを再起動します。**保存済みのタスクはすべて消えます。**

Azure ポータルでデータベースを開き、左メニューの「クエリ エディター」から実行します。

```sql
DROP TABLE dbo.todos;
```

**クエリ エディターにもファイアウォール規則が必要です。** 必要なのは**ブラウザを動かしている端末の IP アドレス**で、VM の送信元 IP ではありません。エラーが出た場合は、その中の「Allowlist IP ...」を選ぶとその場で追加できます。

続けてアプリを再起動します。

```bash
sudo systemctl restart todo
```

**再起動が必要な理由** — アプリは「テーブルを用意した」ことをプロセスごとに覚えているためです。削除しただけでは、次のアクセスで作り直しません。再起動のあと画面を開くと、新しい定義で作成されます。

## SSH で接続できない

### `Connection timed out` になる

**原因** — NSG の受信規則で、22 番の許可 IP が現在の送信元と一致していません。**Cloud Shell の送信元 IP はセッションごとに変わることがあります。**

**影響** — 応答がないまま待たされ、最終的にタイムアウトします。

**対処** — Cloud Shell で現在の IP を確認し、NSG の規則を更新します。

```bash
curl -s https://api.ipify.org
```

表示された IP を、Azure ポータルの NSG の受信規則（22 番）のソースへ設定します。

### `Permission denied (publickey)` になる

**原因** — 秘密鍵のパーミッションが緩いか、鍵が VM の公開鍵と対応していません。

**対処** — パーミッションを確認します。

```bash
chmod 400 ~/.ssh/ssh-key.pem
```

**Cloud Shell へアップロードし直した直後は、権限が戻っています。** 毎回設定してください。

### 「REMOTE HOST IDENTIFICATION HAS CHANGED」と警告される

**原因** — 以前に使った VM と同じパブリック IP アドレスが、新しい VM に割り当てられました。VM を作り直すと起こります。

**影響** — 次の警告が出て接続できません。

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
```

**対処** — その IP アドレスの古い記録だけを消します。

```bash
ssh-keygen -R <VM のパブリック IP>
```

**VM を作り直した覚えがない場合は、消さずに調べてください。** この警告は本来、接続先が別のサーバーにすり替わったことを知らせるものです。

## `Could not get lock` で apt が失敗する

**原因** — 作成直後の VM では自動更新（`unattended-upgrades`）が動いていることがあります。同時に `apt-get` を実行すると、パッケージ管理のロックを取れずに失敗します。

**影響** — git の導入が進みません。VM やアプリには影響しません。

**対処** — **1 分ほど待って、同じコマンドをもう一度実行してください。** 自動更新が終われば通ります。

```bash
sudo apt-get update && sudo apt-get install -y git
```

待っても直らない場合は、動いているプロセスを確認します。

```bash
ps aux | grep -c "[a]pt\|[u]nattended"
```

**`deploy/setup.sh` はこの問題に対処済みです。** 最初の `apt-get` を実行する前に、自動更新のユニットが終わるまで待ちます。**手で打つコマンドだけが対象です。**

## ブラウザに 502 Bad Gateway が表示される

**原因** — nginx は動いていますが、転送先の gunicorn が応答していません。

**影響** — 画面が表示されません。

**対処** — サービスの状態とログを確認します。

```bash
systemctl status todo
sudo journalctl -u todo -n 50 --no-pager
```

**`.env` の記入誤りでは 502 になりません。** 接続に失敗しても画面にメッセージが出るだけで、プロセスは動き続けます。502 は、gunicorn のプロセスそのものが起動していないことを示します。ログで起動時のエラーを確認してください。

`Active: activating (auto-restart)` が繰り返される場合、`src/app.py` の読み込みに失敗しています。5 回連続で失敗すると `failed` になり、状態から判別できます。

## ブラウザに 504 Gateway Time-out が表示される

**原因** — nginx が待っている間に、gunicorn からの応答が返りませんでした。

**影響** — 画面が表示されません。

**対処** — データベースの復帰待ちが nginx の上限を超えた可能性があります。`journalctl` でアプリのログを確認し、`HYT00` や `40613` が続いているなら無料 vCore 秒の残量を確認してください。

`todo.nginx.conf` の `proxy_read_timeout` を短くしていないかも確認してください。**nginx の既定値のままでは復帰を待てません。** 設定すべき値は[設計書の「タイムアウト」](design.md#タイムアウト)にあります。

## Cloud Shell のセッションが切れた

**原因** — Cloud Shell は 20 分の無操作でタイムアウトします。**エフェメラルセッションでは、`$HOME` に置いたファイルがセッション終了とともに消えます。**

**影響** — アップロードした秘密鍵が失われ、SSH で接続できなくなります。**VM 自体とアプリは動き続けます。**

**対処** — 秘密鍵をもう一度アップロードします。手順は[構築手順の「秘密鍵の配置」](build-todo-app.md#5-秘密鍵の配置)を参照してください。

**ハンズオンの区切りごとに環境ごと作り直す場合は、この対処は不要です。**

## ブラウザから VM にアクセスできない

**原因** — 次の 3 つが考えられます。**80 番は送信元を制限していないため、許可 IP のずれは原因になりません。**

| 原因                      | 見分け方                                      |
| ------------------------- | --------------------------------------------- |
| アドレスの取り違え        | **SSH に使うアドレスと同じか**確認します      |
| NSG に 80 番の規則がない  | ポータルで受信規則の一覧を確認します          |
| アプリまたは nginx が停止 | SSH で接続し、`systemctl status` を確認します |

**ブラウザで開くアドレスは、SSH の接続先と同じ VM のパブリック IP です。** ポータルに表示されるプライベート IP（`10.` で始まるもの）ではありません。

**影響** — ページが表示されません。SSH では接続できるのに画面だけ出ない場合は、下の 2 つを疑ってください。

**対処** — まず VM のパブリック IP を確認します。次に、Azure ポータルで NSG の受信規則に 80 番（ソースは `Any`）があるかを確認します。どちらも問題なければ、VM 上で次を実行します。

```bash
systemctl status todo nginx --no-pager
```

**`todo` が停止している場合は**[「ブラウザに 502 Bad Gateway が表示される」](#ブラウザに-502-bad-gateway-が表示される)を参照してください。

## 接続が途中で切れる

**アイドル状態の接続が切断されても、アプリは影響を受けません。** 対処は不要です。理由は[設計書の「接続プールを使わない」](design.md#接続プールを使わない)を参照してください。

## terraform apply が拡張機能で失敗する

**原因** — VM の中で実行されるセットアップが、途中でエラーになっています。Terraform のエラーメッセージには要約しか出ません。

**影響** — `apply` が失敗し、アプリは動きません。**VM 自体は作成済みのため、SSH で接続して調べられます。**

**対処** — SSH で接続し、実行の記録を確認します。**いずれも `sudo` が必要です。**

| 見るもの             | パス                                                                          |
| -------------------- | ----------------------------------------------------------------------------- |
| どこまで進んだか     | `/var/lib/waagent/custom-script/download/0/stdout`                            |
| エラーの内容         | `/var/lib/waagent/custom-script/download/0/stderr`                            |
| 実行されたスクリプト | `/var/lib/waagent/custom-script/download/0/script.sh`                         |
| 拡張機能の動作履歴   | `/var/log/azure/Microsoft.Azure.Extensions.CustomScript/handler.log`          |
| コマンドの実行結果   | `/var/log/azure/Microsoft.Azure.Extensions.CustomScript/CommandExecution.log` |

まず標準エラーの末尾を見ます。

```bash
sudo tail -30 /var/lib/waagent/custom-script/download/0/stderr
```

**成功した場合、これらのファイルは残ります。** 失敗の調査だけでなく、何が実行されたかの確認にも使えます。

**`script.sh` には接続情報が含まれます。** 所有者は root で、権限は 500 です。**内容を貼り付けて共有しないでください。**

**原因を直したら、同じ Cloud Shell のセッションで作り直します。**

```bash
cd ~/mssql-todo-app/labs/sections/section04-web-server/01-create-todo-environment
export TF_VAR_resource_group_name="<リソースグループ名>"
terraform apply
```

**`terraform destroy` は使いません。** 作りかけのリソースが残っていても `apply` は続きから進みます。片付けはリソースグループごとの削除に統一しています。

**セッションが切れていた場合は、この方法が使えません。** `terraform.tfstate` が消えているためです。**Azure ポータルでリソースグループごと削除してから、[コース内ラボ](../labs/sections/section04-web-server/01-create-todo-environment/README.md)をやり直してください。**
