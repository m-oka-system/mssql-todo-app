# 自動スケールを検証する環境を構築する

## Mission

**Terraform で、仮想マシン スケールセットを作る手前までの環境を構築します。** ネットワーク・SSH 鍵・Azure SQL Database ができた状態から、ロードバランサとスケールセットの作成、自動スケールの検証を演習できます。

**ロードバランサとスケールセットは作りません。** どちらも演習で扱う対象のためです。

**仮想マシンも作りません。** インスタンスはスケールセットが作ります。**SSH 鍵は作ります。** スケールセットの作成画面で必須の項目のためです。

| 作られるもの                           | 内容                                                   |
| -------------------------------------- | ------------------------------------------------------ |
| 仮想ネットワーク・サブネット・受信規則 | `vnet`・`snet-vm`・`nsg-vm`                            |
| NAT Gateway とパブリック IP            | `natgw`・`pip-natgw`。インスタンスの送信経路           |
| SSH 鍵                                 | `sshkey-vm-<ランダム>`。作成画面で選びます             |
| Azure SQL Database（無料オファー）     | `sql-<ランダム>` と `todo`                             |
| SQL のファイアウォール規則             | `natgw`。NAT Gateway のパブリック IP を許可します      |
| カスタム データ用のスクリプト          | 接続情報を埋めた版を `terraform output` で取り出せます |

| 作られないもの            | 理由                                     |
| ------------------------- | ---------------------------------------- |
| ロードバランサ            | 受講者がポータルで作ります（演習の対象） |
| 仮想マシン スケールセット | 受講者がポータルで作ります（演習の対象） |
| 仮想マシン                | スケールセットが作ります                 |

## 注意事項

> [!CAUTION]
> このラボは Udemy のコース内ラボ環境（ワークスペース）での実施を前提としています。
> ご自身の Azure サブスクリプションなどコース外の環境で実施すると、リソースの利用料金が発生します。
> コース外の環境で発生した課金について、講師は一切の責任を負いかねますのであらかじめご了承ください。

**このアプリにはログイン認証がありません。** URL に到達した人は誰でもタスクを追加・削除できます。動作確認用のタスク以外を入力しないでください。

**インスタンスへ SSH で接続する手順はありません。** パブリック IP を付けないためです。インスタンスの中でコマンドを実行する場面では、Azure CLI の `az vmss run-command` を使います。

**インスタンスの送信経路は NAT Gateway です。** インスタンスは起動した直後にアプリを取得するため、その時点でインターネットへの経路が要ります。**Terraform が先に用意するので、ロードバランサに送信規則は作りません。**

## 事前準備

1. Azure Cloud Shell（Bash）を起動します。**ストレージの確認を求められたら「ストレージ アカウントは必要ありません」を選びます**（エフェメラル）
2. **ご自身のサブスクリプションで実行する場合のみ**、使用するリソースグループ名を宣言します

   ```bash
   export TF_VAR_resource_group_name="rg-iaas"
   ```

   **コース内ラボ環境では不要です。** 用意されたリソースグループを自動で検出します。

   **リソースグループが空でない場合は中止します。** 片付けはリソースグループごとの削除のため、他のリソースと同居させません。

   **2 回目以降はそのまま進みます。** 前回の記録（`terraform.tfstate`）があれば、同じ構成を当て直すだけになるためです。差分がなければ `No changes.` で終わります。

3. 次のコマンドを実行します（3〜5 分かかります）

   ```bash
   curl -fsSL https://raw.githubusercontent.com/m-oka-system/mssql-todo-app/refs/heads/main/labs/sections/section09/setup.sh | bash
   ```

4. `Apply complete!` と表示されたら作成完了です

**リソースグループは作りません。** 既にあるものの中へリソースを作ります。

## Challenge

### 作られたものを確認する

Azure ポータルでリソースグループを開き、次が作られていることを確認します。

| リソース                         | 名前                   |
| -------------------------------- | ---------------------- |
| 仮想ネットワーク                 | `vnet`                 |
| サブネット                       | `snet-vm`              |
| ネットワークセキュリティグループ | `nsg-vm`               |
| NAT ゲートウェイ                 | `natgw`                |
| パブリック IP アドレス           | `pip-natgw`            |
| SSH キー                         | `sshkey-vm-<ランダム>` |
| SQL サーバー                     | `sql-<ランダム>`       |
| SQL データベース                 | `todo`                 |

**仮想マシンは 1 台もありません。** この時点では正常です。

**`natgw` は `snet-vm` に関連付けられています。** サブネットの「NAT ゲートウェイ」の欄で確認できます。

**SKU は StandardV2 です。** ゾーン冗長で、リージョン内のすべての可用性ゾーンから送信できます。スケールセットが 3 つのゾーンへ分散しても、送信が 1 つのゾーンに依存しません。

**SQL サーバーのファイアウォール規則には `natgw` が登録済みです。** 「ネットワーク」の画面で、`pip-natgw` と同じ IP が入っていることを確認できます。**インスタンスが何台に増えても、送信元はこの 1 つです。**

### スケールセットとロードバランサを作る

**ここからはポータルで作ります。** ロードバランサはスケールセットの作成画面から同時に作ります。設定のうち、このラボで決まっているものは次のとおりです。

| 設定                               | 値                                                         |
| ---------------------------------- | ---------------------------------------------------------- |
| 名前                               | `vmss`                                                     |
| オーケストレーション モード        | 均一（Uniform）                                            |
| イメージ                           | Ubuntu Server 24.04 LTS                                    |
| サイズ                             | `Standard_F1as_v7`（1 vCPU）                               |
| 認証の種類                         | SSH 公開キー                                               |
| SSH 公開キーのソース               | Azure に格納されている既存のキー（`sshkey-vm-<ランダム>`） |
| 可用性ゾーン                       | 1・2・3                                                    |
| インスタンス数                     | 1                                                          |
| スケーリング ポリシー              | 手動（自動スケールは後で設定します）                       |
| 仮想ネットワーク                   | `vnet` / `snet-vm`                                         |
| パブリック IP アドレス             | なし                                                       |
| ネットワーク セキュリティ グループ | なし（サブネットに `nsg-vm` が適用済みです）               |
| 負荷分散オプション                 | Azure ロード バランサー（新規作成）                        |
| カスタム データ                    | `terraform output` で表示した内容をすべて貼り付けます      |

**インスタンス数は 1 で始めます。** 自動スケールの下限に合わせています。**送信経路は NAT Gateway が用意済みのため、作成した直後からアプリの取得が始まります。**

**オーケストレーション モードの既定はフレキシブルです。** このラボでは均一を選びます。インスタンスがスケールセットの子リソースになり、`az vmss` のコマンドでまとめて操作できます。**モードは作成後に変更できません。**

カスタム データは次のコマンドで表示します。**`terraform apply` の最後に `show_custom_data` として表示されるものと同じです。**

```bash
cd ~/mssql-todo-app/labs/sections/section09 && terraform output -raw vmss_custom_data
```

**`terraform apply` の最後に `vmss_custom_data = <sensitive>` と出るのは正常です。** データベースのパスワードを含むため、中身は画面に出しません。**`-raw` を付けて取り出します。** 付けないとここでも `<sensitive>` としか表示されません。

**ラボのディレクトリで実行します。** `terraform output` は実行したディレクトリの記録（`terraform.tfstate`）を読みます。

**表示した内容にはデータベースのパスワードが入っています。** 画面共有や録画の際は表示しないでください。

**貼り付ける内容は書き換えません。** 接続情報は `terraform apply` が埋めています。

**ロードバランサの設定は変えません。** 作成画面から作ると、負荷分散規則（TCP のフロントエンド 80 番 → バックエンド 80 番）と正常性プローブが自動で作られます。**セッション永続化も「なし」が既定です。** 有効にすると、同じ端末からは同じインスタンスに届き続けます。

**送信規則は作りません。** 送信は NAT Gateway が担当します。**NAT Gateway は他の送信方法より優先されるため、送信規則を作っても使われません。**

**受信規則の追加は要りません。** `nsg-vm` は 80 番を Internet へ公開済みで、正常性プローブは既定の規則（`AllowAzureLoadBalancerInBound`）で通ります。

### 動作を確認する

**アプリが応答するまで、インスタンスの起動から 3〜5 分かかります。** ODBC ドライバや uv の導入が終わるまで待ちます。**自動スケールで増えたインスタンスも同じだけ待ちます。**

```bash
curl http://<フロントエンド IP>/healthz
```

ホスト名を含む JSON が返れば、アプリが動いています。ブラウザで `http://<フロントエンド IP>/` を開き、Todo の一覧が出ればデータベースへも到達できています。

**一覧が 503 になる場合は、SQL のファイアウォール規則を確認してください。** `natgw` の規則が `pip-natgw` と同じ IP になっているかを見ます。

### 自動スケールの規則を設定する

ポータルでスケールセットの「スケーリング」を開き、カスタム自動スケールを設定します。

| 設定           | 値                                                    |
| -------------- | ----------------------------------------------------- |
| インスタンス数 | 最小 1・最大 3・既定 1                                |
| スケールアウト | CPU 使用率の平均が 5 分間 70% を超えたら 1 台増やす   |
| スケールイン   | CPU 使用率の平均が 5 分間 25% を下回ったら 1 台減らす |
| クールダウン   | 5 分                                                  |

**最小を 1 にします。** 起動を確認した 1 台から、そのまま自動スケールへ移るためです。

**最大を 3 にします。** コース内ラボ環境のクォータを超えないようにするためです。

### 負荷をかける

インスタンスの CPU を使い切らせます。

```bash
RG="<リソースグループ名>"

az vmss run-command invoke \
  -g "$RG" \
  -n vmss \
  --instance-id "$(az vmss list-instances -g "$RG" -n vmss --query "[0].instanceId" -o tsv)" \
  --command-id RunShellScript \
  --scripts 'for i in $(seq 1 $(nproc)); do timeout 600 yes > /dev/null & done; wait'
```

**インスタンス ID を固定で書きません。** スケールインで消えた ID を指定すると、次のエラーになります。

```text
(InvalidParameter) The provided instanceId 0 is not an active Virtual Machine Scale Set VM instanceId.
```

**残る ID は予測できません。** 既定のスケールイン ポリシーは、ゾーンと障害ドメインの均衡を先に見て、最後にインスタンス ID の大きいものを消します。**先の 2 つが効くと、ID の小さいインスタンスが消えます。** 現在の ID は次で確認できます。

```bash
az vmss list-instances -g "$RG" -n vmss -o table
```

**やり直す場合は 1 台に戻ってからにします。** 2 台のときに 1 台だけへ負荷をかけても、平均は 50% ほどにとどまりスケールアウトしません。

**`yes > /dev/null` を vCPU の数だけ動かします。** 出力を捨てるだけの処理で CPU を使い切ります。

**コマンドが戻るまで約 10 分かかります。** 時間を決めているのは `timeout 600` です。`wait` は背景に回した `yes` が終わるまで待つだけで、それ自体に時間の定義はありません。**短くしたい場合は `timeout` の秒数を変えます。**

**その間、端末は塞がります。** スケールアウトはコマンドの実行中に起きるため、様子はポータルのインスタンス一覧で見ます。

**途中では止められません。** Run Command は実行中のスクリプトをキャンセルできず、同じインスタンスへ次のコマンドも投げられません（同時に 1 本まで）。**`timeout` が切れるまで待ちます。**

**スケールアウトまで 5〜6 分かかります。** 規則が「5 分間の平均」を見るためです。

**増えたインスタンスには負荷がかかりません。** 平均が下がるため、3 台まで一気に増えることはありません。

## 確認

次の 4 つが確認できれば完了です。

| 確認すること                           | 方法                                                               |
| -------------------------------------- | ------------------------------------------------------------------ |
| ロードバランサ経由で届くこと           | フロントエンド IP へ `curl http://<IP>/healthz` を実行する         |
| スケールアウトすること                 | 負荷をかけて 5〜6 分後、ポータルのインスタンス一覧が 2 台になる    |
| 振り分けられていること                 | 2 台になったあと同じコマンドを繰り返し、`hostname` が変わる        |
| 増えたインスタンスも同じ画面を返すこと | ブラウザで `http://<IP>/` を開き、どのホスト名でも同じ Todo が並ぶ |

**スケールインは負荷が止まってから 5〜10 分後です。** 規則の期間とクールダウンを待つためです。

**ブラウザで再読み込みしても、応答するインスタンスが変わらないことがあります。** ロードバランサは接続ごとに振り分け先を決めるため、ブラウザが接続を使い回すと同じインスタンスに届き続けます。**`curl` を繰り返すのが確実です。**

**画面の下端に、応答したインスタンスのホスト名が出ます。** `/healthz` の応答にも同じものが入ります。

```json
{ "hostname": "vmss6z7lb000000", "private_ip": "10.0.1.4", "db_name": "todo" }
```

**ホスト名はスケールセットの名前そのものではありません。** ポータルが作るコンピューター名のプレフィックスに、6 桁の連番が付いた形になります。

## 片付け

**確認が終わったら、Azure ポータルでリソースグループごと削除してください。**

**`terraform destroy` は使いません。** Terraform はリソースグループ自体を管理しておらず、作成したものはすべてその中にあります。**リソースグループを消せば確実に片付きます。** ポータルで作ったロードバランサとスケールセットも同時に消えます。

**NAT Gateway は使っていなくても時間で課金されます。** ご自身のサブスクリプションで実施した場合は、残さず削除してください。

**環境を残すとデータベースの無料枠を消費し続けます。** 外部からのアクセスが届き続けると自動一時停止が働かず、**約 1.7 日**で使い切ります。**使い切っても料金は発生しません。** 上限はデータベースごとに数えるため、リソースグループごと削除してこのラボを実行し直せば復旧します。

### Cloud Shell に残るファイル

`terraform apply` は次の 2 つを、実行した端末に作ります。

| ファイル                        | 内容                                      |
| ------------------------------- | ----------------------------------------- |
| `~/.ssh/ssh-key-<ランダム>.pem` | **SSH の秘密鍵**                          |
| `terraform.tfstate`             | リソースの状態・接続情報・カスタム データ |

**カスタム データはファイルとして書き出しません。** `terraform.tfstate` の中だけに残ります。

**エフェメラル（ストレージなし）で起動した場合は、セッションが切れるとまとめて消えます。** 事前準備の手順 1 で選んでいれば、操作は不要です。

**ストレージをマウントしている場合は残り続けます。** 次を実行して消してください。

```bash
rm -rf ~/mssql-todo-app ~/.ssh/ssh-key-*.pem
```

## 補足

**`terraform apply` を実行した端末の IP は、SSH の受信規則へ自動で許可されます。** 別の端末からも操作する場合は、`setup.sh` ではなく手で実行し、変数を追加します。

```bash
cd ~/mssql-todo-app/labs/sections/section09
export TF_VAR_resource_group_name="<リソースグループ名>"
terraform apply -var='allowed_client_ip=["<IP>"]'
```

**`TF_VAR_resource_group_name` の宣言が要ります。** `setup.sh` が設定した値はスクリプトのプロセス内だけのもので、Cloud Shell には残りません。省くと入力待ちで止まります。

**SQL サーバーのファイアウォールに登録されるのは `natgw` の IP だけです。** `allowed_client_ip` は SSH の受信規則にしか効きません。ポータルのクエリエディターを使う場合は、同じ画面で自分の IP を追加してください。

**カスタム データの台本は [`deploy/vmss-portal-setup.sh`](../../../deploy/vmss-portal-setup.sh) です。** `terraform apply` はこのファイルのプレースホルダを接続情報へ置き換え、`vmss_custom_data` として出力します。**中身は 1 か所にしかありません。**

**インスタンスへ SSH したい場合は、ロードバランサへインバウンド NAT プールを追加します。** 秘密鍵は `~/.ssh/ssh-key-<ランダム>.pem` にあり、ユーザー名は作成時に指定したものです。

**正常性プローブを `/healthz` に変えると、より確実になります。** 既定のプローブは 80 番が開いているかを見るだけで、アプリが応答できるかまでは見ません。**[ロードバランサのラボ](../section08/README.md)では変更します。** そちらはデータベースがなく、`/` が 503 を返すためです。

**送信経路にはロードバランサの送信規則という選択肢もあります。** このラボが NAT Gateway を使うのは、**スケールセットより先に送信の口を用意できる**ためです。送信規則はロードバランサができるまで作れず、それまでに起動したインスタンスはアプリを取得できません。**2 つの違いは[ロードバランサのラボ](../section08/README.md#パブリック-ip-を付けない構成での送信経路)にまとめています。**

**ロードバランサだけを扱う[ラボ](../section08/README.md)もあります。** そちらは VM 2 台構成で、データベースを作りません。
