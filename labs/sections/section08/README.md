# ロードバランサの振り分け先を構築する

## Mission

**Terraform で、ロードバランサの振り分け先になる VM を 2 台構築します。** アプリが動いている状態から、ロードバランサの作成と負荷分散の確認を演習できます。

**ロードバランサは作りません。** 演習で扱う対象のためです。

**Azure SQL Database も作りません。** 負荷分散の確認に使うのは、どの VM が応答したかを返す `/healthz` だけで、この URL はデータベースに接続しないためです。

| 作られるもの                           | 内容                                         |
| -------------------------------------- | -------------------------------------------- |
| 仮想ネットワーク・サブネット・受信規則 | `vnet`・`snet-vm`・`nsg-vm`                  |
| SSH 鍵と VM 2 台                       | `vm01`・`vm02`。どちらもパブリック IP を持つ |
| アプリの取得・セットアップ・起動       | 2 台とも同じアプリが 80 番で応答する         |

| 作られないもの     | 理由                                            |
| ------------------ | ----------------------------------------------- |
| ロードバランサ     | 受講者がポータルで作ります（演習の対象）        |
| Azure SQL Database | 負荷分散の確認に要りません（`/healthz` で行う） |

## 注意事項

> [!CAUTION]
> このラボは Udemy のコース内ラボ環境（ワークスペース）での実施を前提としています。
> ご自身の Azure サブスクリプションなどコース外の環境で実施すると、リソースの利用料金が発生します。
> コース外の環境で発生した課金について、講師は一切の責任を負いかねますのであらかじめご了承ください。

**このラボでは Todo の一覧を開けません。** データベースを作らないため、`http://<IP>/` はエラー画面（HTTP 503）になります。**表示までに 1 分以上かかります。** アプリが接続を数回やり直してから諦めるためです。**確認には `/healthz` を使ってください。**

**このアプリにはログイン認証がありません。** URL に到達した人は誰でも操作できます。

## 事前準備

1. Azure Cloud Shell（Bash）を起動します。**ストレージの確認を求められたら「ストレージ アカウントは必要ありません」を選びます**（エフェメラル）
2. **ご自身のサブスクリプションで実行する場合のみ**、使用するリソースグループ名を宣言します

   ```bash
   export TF_VAR_resource_group_name="rg-iaas"
   ```

   **コース内ラボ環境では不要です。** 用意されたリソースグループを自動で検出します。

   **リソースグループが空でない場合は中止します。** 片付けはリソースグループごとの削除のため、他のリソースと同居させません。

   **2 回目以降はそのまま進みます。** 前回の記録（`terraform.tfstate`）があれば、同じ構成を当て直すだけになるためです。差分がなければ `No changes.` で終わります。

3. 次のコマンドを実行します（5〜10 分かかります）

   ```bash
   curl -fsSL https://raw.githubusercontent.com/m-oka-system/mssql-todo-app/refs/heads/main/labs/sections/section08/setup.sh | bash
   ```

4. `Apply complete!` と表示されたら作成完了です

**リソースグループは作りません。** 既にあるものの中へリソースを作ります。

**`terraform apply` が完了した時点で、2 台ともアプリが応答します。** 拡張機能の完了まで Terraform が待つためです。

## Challenge

### 作られたものを確認する

Azure ポータルでリソースグループを開き、次が作られていることを確認します。

| リソース                         | 名前           |
| -------------------------------- | -------------- |
| 仮想ネットワーク                 | `vnet`         |
| サブネット                       | `snet-vm`      |
| ネットワークセキュリティグループ | `nsg-vm`       |
| 仮想マシン                       | `vm01`・`vm02` |

### 次に打つコマンドを確認する

**`terraform apply` の最後に `next_steps` として表示されます。** 画面を流してしまった場合は、実行したディレクトリで取り出せます。

```bash
cd ~/mssql-todo-app/labs/sections/section08
terraform output -raw next_steps
```

**`-raw` を付けないと `<<EOT` と `EOT` が付きます。** 付けなくても内容は読めます。

### ロードバランサを作る

**ここからはポータルで作ります。** 設定のうち、このラボで決まっているものは次のとおりです。

| 設定               | 値                                             |
| ------------------ | ---------------------------------------------- |
| SKU                | Standard                                       |
| バックエンドプール | `vm01`・`vm02`                                 |
| ヘルスプローブ     | HTTP・ポート 80・パス `/healthz`               |
| 負荷分散規則       | TCP・フロントエンド 80 番 → バックエンド 80 番 |
| セッション永続化   | なし                                           |

**ヘルスプローブのパスに `/` を指定しないでください。** データベースを作らないこのラボでは 503 が返り、2 台とも異常と判定されて振り分け先がなくなります。**`/healthz` はデータベースに接続しません。**

**セッション永続化を有効にすると、同じ端末からは同じ VM に届き続けます。** 振り分けを確認する段階では「なし」のままにします。

**受信規則の追加は要りません。** `nsg-vm` は 80 番を Internet へ公開済みで、ヘルスプローブは既定の規則（`AllowAzureLoadBalancerInBound`）で通ります。

## 確認

次の 3 つが確認できれば完了です。

| 確認すること                 | 方法                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| 2 台とも単体で応答すること   | `next_steps` の 1 番。ホスト名を含む JSON が返る                |
| ロードバランサ経由で届くこと | フロントエンド IP へ `curl http://<IP>/healthz` を実行する      |
| 振り分けられていること       | 同じコマンドを繰り返し、`hostname` が `vm01` と `vm02` で変わる |

**ブラウザで再読み込みしても、応答する VM が変わらないことがあります。** ロードバランサは接続ごとに振り分け先を決めるため、ブラウザが接続を使い回すと同じ VM に届き続けます。**`curl` を繰り返すのが確実です。**

**同じホスト名が数回続くこともあります。** 振り分け先はハッシュで決まるもので、順番に配るものではありません。

## 片付け

**確認が終わったら、Azure ポータルでリソースグループごと削除してください。**

**`terraform destroy` は使いません。** Terraform はリソースグループ自体を管理しておらず、作成したものはすべてその中にあります。**リソースグループを消せば確実に片付きます。** ポータルで作ったロードバランサも同時に消えます。

### Cloud Shell に残るファイル

`terraform apply` は次の 2 つを、実行した端末に作ります。

| ファイル                        | 内容            |
| ------------------------------- | --------------- |
| `~/.ssh/ssh-key-<ランダム>.pem` | **VM の秘密鍵** |
| `terraform.tfstate`             | リソースの状態  |

**`src/.env` は作られません。** データベースを作らないラボのためです。

**エフェメラル（ストレージなし）で起動した場合は、セッションが切れるとまとめて消えます。** 事前準備の手順 1 で選んでいれば、操作は不要です。

**ストレージをマウントしている場合は残り続けます。** 次を実行して消してください。

```bash
rm -rf ~/mssql-todo-app ~/.ssh/ssh-key-*.pem
```

## 補足

**`terraform apply` を実行した端末の IP は、SSH の受信規則へ自動で許可されます。** 別の端末からも接続する場合は、`setup.sh` ではなく手で実行し、変数を追加します。

```bash
cd ~/mssql-todo-app/labs/sections/section08
export TF_VAR_resource_group_name="<リソースグループ名>"
terraform apply -var='allowed_client_ip=["<IP>"]'
```

**`TF_VAR_resource_group_name` の宣言が要ります。** `setup.sh` が設定した値はスクリプトのプロセス内だけのもので、Cloud Shell には残りません。省くと入力待ちで止まります。

**接続情報（`/opt/todo/src/.env`）は空欄で配置されています。** アプリは起動しており、`/healthz` は応答します。**Todo の一覧まで動かす構成は[セクション 09](../section09/README.md) にあります。**

**VM にはパブリック IP が付いています。** ロードバランサを作る前に 1 台ずつ確認するためと、サブネットが既定の送信アクセスを無効にしているためです。付けないと VM がインターネットへ出られず、アプリの取得ができません。
